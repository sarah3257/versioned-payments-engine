# איך מפרסמים מודל חדש — שלבים מעשיים

אפשר לעבוד במסך "פרסום דרך API" או עם קובץ `examples/requests.http`. הנתיבים הם שלנו, לא של SAS.

## סדר הפרסום

1. מפרסמים פריטי מחירון ושיעורי מס הדרושים לחישוב.
2. מפרסמים גרסאות רכיבים עם מפרט מתאים לסוגם.
3. מפרסמים גרסת מודל המפנה למזהי הרכיבים ומסדרת שכבות.
4. מוסיפים הסכמת מסגרת כשעוברים לגרסת מודל חדשה.
5. מריצים סימולציה ומשווים לתוצאה צפויה שאושרה מחוץ למערכת.
6. מריצים חישוב שמור עם RequestKey חדש.

ה־API הוא "פרסום ישיר של גרסה מאושרת". מחזור טיוטה/אישור משתמשים טרם נבנה. כעת את עריכת הטיוטה עושים בקובץ JSON/textarea; המידע לא פעיל לפני POST מוצלח.

## דוגמה: מודל חדש שרק מרכיב רכיבים קיימים

`POST /api/models/publish`

```json
{
  "modelId": 2,
  "version": 1,
  "name": "מודל נוסף — אחזקה ורווח ומס",
  "from": "2026-01-01",
  "to": "2027-12-31",
  "components": [
    { "componentId": 1, "layer": 1, "order": 1 },
    { "componentId": 10, "layer": 6, "order": 1 },
    { "componentId": 11, "layer": 7, "order": 1 }
  ]
}
```

אין פיתוח קוד למודל הזה. הוא משתמש ברכיבי ההדגמה. לשם חישוב החליפי את ModelId בבקשת ההשמה ל־2. לפני הסכמה ראשונה המנוע בוחר בגרסה הראשונית, בהתאם למדיניות ה־POC המתועדת.

## דוגמה: אחזקה בגרסה חדשה ללא שינוי המודל

`POST /api/components/publish`

```json
{
  "componentId": 1,
  "version": 4,
  "name": "אחזקה — שינוי אחוז ביגוד",
  "kind": "Maintenance",
  "from": "2026-11-01",
  "to": "2027-12-31",
  "items": [
    { "priceKey": "clothes", "factor": 1.2, "profitRequired": true, "taxLiability": "Both" },
    { "priceKey": "municipal", "factor": 0.9, "profitRequired": true, "taxLiability": "Both" }
  ],
  "rows": []
}
```

מפרסמים מפרט מלא של הגרסה, לא PATCH של שדה. בחישוב נובמבר תיבחר גרסה 4; באוגוסט גרסה 1. המודלים עדיין מצביעים ל־ComponentId=1 ואין פרסום מודל מחדש. שליחה חוזרת של אותו מספר גרסה נדחית; צריך לבדוק תחילה אם הפרסום כבר הצליח.

## דוגמה: גרסת מודל חדשה

אותו ModelId עם Version גבוה יותר, רשימת Components מלאה ותוקף. הסרת רכיב או שינוי שכבה הם שינוי גרסת מודל. כדי שמסגרת תעבור לגרסה החדשה מפרסמים:

```json
{ "institution": 9999, "modelId": 1, "modelVersion": 2, "effectiveFrom": "2026-10-01" }
```

הנתיב: `POST /api/consents`. אירוע קודם לתחולת ההסכמה נשאר עם המודל הקודם. תאריך הסכמה זהה לאותו מודל ומסגרת אינו ניתן לדריסה; תהליך תיקון/ביטול הסכמה הוא הרחבה עתידית.

## דוגמה: טבלת החלטה

ב־Basket כל Row הוא כלל עם AND בין Conditions. כל השורות המתאימות נוצרות (COLLECT). Value=null הוא wildcard, לא השוואת ריק. ResultAmount=0 מחייב PriceKey תקף. קיימים אופרטורים =, !=, <, >, <=, >=, BETWEEN; המאפיינים המותרים מוצגים במסמך ה־API. אין הרצת ביטויי C# חופשיים מנתונים.

```json
{
  "componentId": 7, "version": 2, "name": "סל חדש", "kind": "Basket",
  "from": "2026-01-01", "to": "2027-12-31", "items": [],
  "rows": [{
    "rowKey": "support", "description": "תוספת תמיכה", "resultAmount": 100,
    "priceKey": null, "taxLiability": "None",
    "conditions": [{ "attribute": "supportLevel", "operator": "BETWEEN", "value": "4", "valueTo": "5" }]
  }]
}
```

אין צורך ליצור מחדש מודל כדי שהגרסה הזאת תשמש אותו בתאריכים המתאימים.
